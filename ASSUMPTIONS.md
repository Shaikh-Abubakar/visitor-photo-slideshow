# Assumptions

> **Important:** everything in this file is an **implementation assumption made by the developer**.
> None of it is an explicit requirement of the assignment brief. Each item can be changed;
> where a change would affect the database or code, the affected part is noted.

Status of this document: written in **Step 1** (foundation and database design). Item B4 was changed in
**Step 1, Correction 1** (consent record for every upload session). Section F was added in **Step 2**
(configuration and database connection). Update it whenever an assumption changes.

---

## A. Assumptions listed for Step 1

| # | Assumption | Where it shows up |
|---|------------|-------------------|
| A1 | Visitors are identified using **unique visitor codes**. | `visitors.visitor_code_hash` (unique) |
| A2 | Visitors do **not** need to provide a phone number or email address. | `visitors` has only `name` and the code hash |
| A3 | A maximum of **10 photographs** can be uploaded per request. | `UPLOAD_MAX_FILES` in `.env` |
| A4 | Each photograph can be at most **5 MB**. Interpreted as 5 × 1024 × 1024 = 5,242,880 bytes. | `UPLOAD_MAX_FILE_SIZE_BYTES` in `.env` |
| A5 | Supported formats are **JPG, JPEG, PNG and WebP**. | `UPLOAD_ALLOWED_MIME_TYPES` in `.env`; `photos.mime_type` |
| A6 | The default photograph display duration is **5 seconds**. | `SLIDESHOW_DEFAULT_DURATION_SECONDS`; overridable via the `settings` table |
| A7 | **Previous photographs are retained** when a visitor returns. | Photos are never replaced; a visitor has many `photos` rows |
| A8 | **Several visitors can upload at the same time.** | Unique server-generated filenames; database transactions |
| A9 | **Public slideshow display requires recorded consent.** | `photos.consent_id` is `NOT NULL` with a foreign key |
| A10 | Uploaded photographs are stored in a **private server directory**, not directly web-accessible. | `storage/uploads/` (or `UPLOAD_STORAGE_PATH`) |

Notes:

* "JPG" and "JPEG" are the same format. Both extensions are accepted, but the stored file
  extension is derived from the detected MIME type, not from the visitor's file name.
* A3 and A4 together mean one request can carry up to 10 × 5 MB = **50 MB**. PHP's default
  limits are much lower (see section C).

## B. Additional design decisions made in Step 1

These were not in the Step 1 list. They were needed to complete the design and are open to change.

| # | Decision | Reason | Easy to change? |
|---|----------|--------|-----------------|
| B1 | Visitor codes are **generated by the system** (random, high entropy) and shown to the visitor once. Visitors do not choose their own code. | Chosen codes are guessable. Random codes make a fast, secure lookup possible. | Yes (application logic) |
| B2 | A code is stored as an **HMAC-SHA-256 hex digest** (64 characters) using a secret `VISITOR_CODE_PEPPER` kept in `.env`. | A salted password hash (bcrypt) cannot be searched by value, so finding a returning visitor would mean checking every row. A keyed hash gives an indexed exact-match lookup and a database leak alone does not reveal codes. | Moderate (changes code and column length) |
| B3 | `photos.status` allows only **`active`** and **`hidden`**. | `active` photos can appear in the slideshow; an administrator can hide one without deleting it. There is no approval queue. | Yes (`ALTER TABLE` the CHECK) |
| B4 | A **new consent record is created for every photo upload session**, even when the consent text version has not changed. Several `consents` rows may therefore share the same visitor and the same `consent_version`. There is **no** unique key on `(visitor_id, consent_version)`; an ordinary index `idx_consents_visitor_version` is used instead. Each photograph references the consent record of the session in which it was uploaded. *(Changed in Correction 1, on the student's instruction; earlier Step 1 design allowed one record per visitor per version.)* | Every upload session has its own record of who agreed, to which consent text, and when. The `consents` table grows by one row per session, which is expected. What exactly counts as one "upload session" is decided when the upload step is built. | Yes (the application decides when to insert a row; the schema allows any number) |
| B5 | All foreign keys use **`ON DELETE RESTRICT`**. | A visitor or consent cannot be deleted while photographs still reference it, so photo files are not orphaned on disk. Deleting must be done deliberately, in order, in a transaction. | Yes |
| B6 | A photograph's consent must belong to the **same visitor** (composite foreign key). | Stops a bug or attack from attaching one visitor's photo to another visitor's consent. | Yes |
| B7 | All times are stored as `DATETIME` in **UTC**. | Avoids differences between Windows and Ubuntu server time zones and daylight-saving changes. | Yes |
| B8 | `schema.sql` contains **no seed data** (no admin account, no default settings rows). | No hardcoded passwords. Defaults live in configuration and are overridden by the `settings` table. | Yes |
| B9 | Photos are ordered and paged by **`id`**, not by timestamp. | `id` only increases, so it gives a stable order and fast "next page" queries. | Yes |
| B10 | The slideshow will advance **without JavaScript**, using a server-side "next photo" request and an HTML meta-refresh. | The project technology restriction forbids JavaScript. **Please confirm** (see section E). | Yes |
| B11 | Documentation files keep the upper-case names required by the brief (`README.md`, `ARCHITECTURE.md`, `ASSUMPTIONS.md`, `AI_LOG.md`). All PHP, SQL and folder names are lower case. | No code loads the documentation files, so Linux case-sensitivity cannot break anything. | n/a |
| B12 | Folder protection uses Apache 2.4 `Require all denied` rules in `.htaccess` files, plus the same rules in the Ubuntu virtual host. | The required folder layout puts `config/` and `storage/` inside the project folder. | Yes |

## C. Environment assumptions

* **PHP 8.2 or newer** with these extensions: `pdo_mysql`, `fileinfo`, `mbstring`. (`gd` is
  only needed if thumbnails are added later.) All are available on Windows and Ubuntu.
* **MySQL 8+ or MariaDB.** XAMPP ships **MariaDB**, not MySQL. The schema avoids features that
  differ between them (explicit collation, standard `CHECK`, no `ENUM`, no JSON).
* **PHP upload limits must be raised.** PHP's built-in defaults are `upload_max_filesize = 2M`,
  `post_max_size = 8M`. They are too small for A3/A4. The README lists the required `php.ini`
  values. Without them uploads fail before the application code runs.
* Apache **2.4**, the version shipped with XAMPP and Ubuntu.

---

## D. Not covered yet (known gaps, deliberately out of Step 1)

* **Consent withdrawal.** The `consents` table (as specified) has no "withdrawn" column. If a visitor
  withdraws consent, the current design cannot record it.
* **Rate limiting and lockout** for visitor-code and admin login attempts.
* **Image processing** (thumbnails, EXIF stripping, resizing).
* **Backups** of the database and the `storage/uploads/` folder.
* **Unlimited scale.** The design is meant to grow, but it has not been load-tested and does not
  claim unlimited users or storage. See `ARCHITECTURE.md`, section 12.

## F. Decisions made in Step 2 (configuration and database connection)

None of these were stated in the Step 2 brief. They are open to change.

| # | Decision | Reason | Easy to change? |
|---|----------|--------|-----------------|
| F1 | Each setting is read from a **real environment variable first, then the `.env` file, then a default**. An **empty value counts as "not set"**. | The brief asks for environment variables with an optional local file for development. Treating empty as unset lets a blank line in `.env` mean "use the default". | Yes (`config_load()`) |
| F2 | The `.env` file is read from the project root. The real environment variable `APP_ENV_FILE` (an absolute path) can point to a file outside the web folder. | `ARCHITECTURE.md` (Step 1) promised that the `.env` location can be outside the web folder. | Yes |
| F3 | Defaults: `APP_ENV=production`, `APP_DEBUG=false`, `APP_URL=http://localhost`, `DB_HOST=127.0.0.1`, `DB_PORT=3306`, `DB_NAME=visitor_photo_slideshow`, empty `DB_PASSWORD`. **`DB_USER` has no default and is required.** | Safe when nothing is configured; no credentials appear in code. | Yes |
| F4 | `APP_ENV` must be `development`, `testing` or `production`. `APP_DEBUG=true` is **refused** when `APP_ENV=production`. | Prevents error details being shown to visitors by a configuration slip. | Yes |
| F5 | The default database host is **`127.0.0.1`**, not `localhost`. | On Ubuntu `localhost` makes PHP use a socket file and ignore the port; `127.0.0.1` is the same on both systems and matches the user created in the README for `127.0.0.1`. | Yes |
| F6 | Right after connecting, the session time zone is set to **`+00:00`** and the connection collation to **`utf8mb4_unicode_ci`**. The server's `sql_mode` is **not** changed. | UTC and the table collation were already decided in Step 1 (B7 and the schema). Changing `sql_mode` was judged unnecessary. | Yes (`DATABASE_SESSION_SQL`) |
| F7 | One shared connection per request, opened only when first needed. No persistent connections. Connect timeout **5 seconds**. | Brief asks for no unnecessary connections. Persistent connections can carry state between requests. | Yes |
| F8 | PHP's own default time zone is set to **UTC** in the bootstrap. | Matches the database; pages can convert to a local time zone for display later. | Yes |
| F9 | `.env` syntax: `NAME=value`, names in capital letters, `#` comment lines only (no comments after a value), matching quotes are removed, **no escape sequences**. Errors report the line number, never the line. | Simple to explain, works for Windows paths like `D:\private\uploads`, and cannot leak a password in a message. | Yes |
| F10 | Validation limits: `APP_NAME` 1-100 characters; `DB_HOST` and `DB_NAME` limited to letters, digits and a few symbols (they are placed in the connection string); `DB_USER` up to 80 characters; `UPLOAD_MAX_FILE_SIZE_BYTES` 1 to 4,294,967,295 (the largest value of the `INT UNSIGNED` column `photos.file_size`); `UPLOAD_MAX_FILES` 1 or more with no upper limit; `UPLOAD_STORAGE_PATH` must be an absolute path **for the operating system in use**. | Catch mistakes early; protect the connection string. | Yes |
| F11 | `config.php` and `database.php` are in **`config/`**, not `includes/` as `ARCHITECTURE.md` planned in Step 1. | The Step 2 brief names `config/database.php`. | Yes |
| F12 | The loader reads only the settings listed in the Step 2 brief. `VISITOR_CODE_PEPPER`, `UPLOAD_ALLOWED_MIME_TYPES` and `SLIDESHOW_DEFAULT_DURATION_SECONDS` stay in `.env.example` for later steps. | Strict Step 2 scope. | Yes |
| F13 | On web requests, an uncaught exception shows only "Something went wrong. Please try again later." with HTTP 500; the details go to the server log (and to the page only if `APP_DEBUG` is true). | Brief: never expose internal errors to visitors. | Yes |
| F14 | `tests/check_database.php` checks that the five tables exist, **not** their columns. A missing or unwritable upload folder is a warning and does not change the result. The table list is written inside the script. | Matches the brief; the folder may legitimately not exist yet. | Yes |
| F15 | `.env.example` was **rewritten** in Step 2 from the variable list in `ARCHITECTURE.md`, because the Step 1 copy was not available to the AI. | Brief: update `.env.example` with placeholders only. | Compare it with your own copy |
