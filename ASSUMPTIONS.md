## A. Assumptions listed for Step 1

| # | Assumption | Where it shows up |
|---|------------|-------------------|
| A1 | Visitors are identified using **unique visitor codes**. | `visitors.visitor_code_hash` (unique) |
| A2 | Visitors do **not** need to provide a phone number or email address. | `visitors` has only `name` and the code hash |
| A3 | A maximum of **10 photographs** can be uploaded per request. | `UPLOAD_MAX_FILES` in `.env` |
| A4 | Each photograph can be at most **5 MB**. Interpreted as 5 × 1024 × 1024 = 5,242,880 bytes. | `UPLOAD_MAX_FILE_SIZE_BYTES` in `.env` |
| A5 | Supported formats are **JPG, JPEG, PNG and WebP**. | `UPLOAD_ALLOWED_MIME_TYPES` in `.env`; `photos.mime_type` |
| A6 | The default photograph display duration is **5 seconds**. | `SLIDESHOW_DEFAULT_DURATION_SECONDS`; overridable via the `settings` table |
| A7 | **Previous photographs are retained** when a visitor returns. | Photos are never replaced; a visitor has many `photos` rows |
| A8 | **Several visitors can upload at the same time.** | Unique server-generated filenames; database transactions |
| A9 | **Public slideshow display requires recorded consent.** | `photos.consent_id` is `NOT NULL` with a foreign key |
| A10 | Uploaded photographs are stored in a **private server directory**, not directly web-accessible. | `storage/uploads/` (or `UPLOAD_STORAGE_PATH`) |

Notes:

* "JPG" and "JPEG" are the same format. Both extensions are accepted, but the stored file
  extension is derived from the detected MIME type, not from the visitor's file name.
* A3 and A4 together mean one request can carry up to 10 × 5 MB = **50 MB**. PHP's default
  limits are much lower (see section C).

## B. Additional design decisions made in Step 1

These were not in the Step 1 list. They were needed to complete the design and are open to change.

| # | Decision | Reason | Easy to change? |
|---|----------|--------|-----------------|
| B1 | Visitor codes are **generated by the system** (random, high entropy) and shown to the visitor once. Visitors do not choose their own code. | Chosen codes are guessable. Random codes make a fast, secure lookup possible. | Yes (application logic) |
| B2 | *(Step 3: not what is built; the Step 3 brief asked for plain SHA-256, see G1.)* A code is stored as an **HMAC-SHA-256 hex digest** (64 characters) using a secret `VISITOR_CODE_PEPPER` kept in `.env`. | A salted password hash (bcrypt) cannot be searched by value, so finding a returning visitor would mean checking every row. A keyed hash gives an indexed exact-match lookup and a database leak alone does not reveal codes. | Moderate (changes code and column length) |
| B3 | `photos.status` allows only **`active`** and **`hidden`**. | `active` photos can appear in the slideshow; an administrator can hide one without deleting it. There is no approval queue. | Yes (`ALTER TABLE` the CHECK) |
| B4 | A **new consent record is created for every photo upload session**, even when the consent text version has not changed. Several `consents` rows may therefore share the same visitor and the same `consent_version`. There is **no** unique key on `(visitor_id, consent_version)`; an ordinary index `idx_consents_visitor_version` is used instead. Each photograph references the consent record of the session in which it was uploaded. *(Changed in Correction 1, on the student's instruction; earlier Step 1 design allowed one record per visitor per version.)* | Every upload session has its own record of who agreed, to which consent text, and when. The `consents` table grows by one row per session, which is expected. What exactly counts as one "upload session" is decided when the upload step is built. | Yes (the application decides when to insert a row; the schema allows any number) |
| B5 | All foreign keys use **`ON DELETE RESTRICT`**. | A visitor or consent cannot be deleted while photographs still reference it, so photo files are not orphaned on disk. Deleting must be done deliberately, in order, in a transaction. | Yes |
| B6 | A photograph's consent must belong to the **same visitor** (composite foreign key). | Stops a bug or attack from attaching one visitor's photo to another visitor's consent. | Yes |
| B7 | All times are stored as `DATETIME` in **UTC**. | Avoids differences between Windows and Ubuntu server time zones and daylight-saving changes. | Yes |
| B8 | `schema.sql` contains **no seed data** (no admin account, no default settings rows). | No hardcoded passwords. Defaults live in configuration and are overridden by the `settings` table. | Yes |
| B9 | Photos are ordered and paged by **`id`**, not by timestamp. | `id` only increases, so it gives a stable order and fast "next page" queries. | Yes |
| B10 | The slideshow will advance **without JavaScript**, using a server-side "next photo" request and an HTML meta-refresh. | The project technology restriction forbids JavaScript. **Please confirm** (see section E). | Yes |
| B11 | Documentation files keep the upper-case names required by the brief (`README.md`, `ARCHITECTURE.md`, `ASSUMPTIONS.md`, `AI_LOG.md`). All PHP, SQL and folder names are lower case. | No code loads the documentation files, so Linux case-sensitivity cannot break anything. | n/a |
| B12 | Folder protection uses Apache 2.4 `Require all denied` rules in `.htaccess` files, plus the same rules in the Ubuntu virtual host. | The required folder layout puts `config/` and `storage/` inside the project folder. | Yes |

## C. Environment assumptions

* **PHP 8.2 or newer** with these extensions: `pdo_mysql`, `fileinfo`, `mbstring`. (`gd` is
  only needed if thumbnails are added later.) All are available on Windows and Ubuntu.
* **MySQL 8+ or MariaDB.** XAMPP ships **MariaDB**, not MySQL. The schema avoids features that
  differ between them (explicit collation, standard `CHECK`, no `ENUM`, no JSON).
* **PHP upload limits must be raised.** PHP's built-in defaults are `upload_max_filesize = 2M`,
  `post_max_size = 8M`. They are too small for A3/A4. The README lists the required `php.ini`
  values. Without them uploads fail before the application code runs.
* Apache **2.4**, the version shipped with XAMPP and Ubuntu.

## D. Not covered yet (known gaps, deliberately out of Step 1)

* **Consent withdrawal.** The `consents` table (as specified) has no "withdrawn" column. If a visitor
  withdraws consent, the current design cannot record it.
* **Rate limiting and lockout** for visitor-code and admin login attempts.
* **Image processing** (thumbnails, EXIF stripping, resizing).
* **Backups** of the database and the `storage/uploads/` folder.
* **Unlimited scale.** The design is meant to grow, but it has not been load-tested and does not
  claim unlimited users or storage. See `ARCHITECTURE.md`, section 12.

## G. Decisions made in Step 3 (visitor registration)

None of these were stated in the Step 3 brief unless marked. They are open to change.

| # | Decision | Reason | Easy to change? |
|---|----------|--------|-----------------|
| G1 | The visitor code is stored as a plain **SHA-256** hash (`hash('sha256', code)`), not the HMAC with `VISITOR_CODE_PEPPER` of B2 and `ARCHITECTURE.md` (Step 1). *The brief asks for SHA-256.* This is a **conflict between the Step 1 design and the Step 3 brief**, resolved in favour of the Step 3 brief. `VISITOR_CODE_PEPPER` is therefore unused. | The brief says SHA-256, and the Step 2 loader does not read the pepper. Because a code has 160 random bits, guessing a code from a stolen hash is not realistic even without a secret; the pepper would add a second layer, not fix a weakness. | **Hard once visitors exist:** switching to HMAC changes every hash, so existing codes would stop working. Decide before real visitors register (question E4). |
| G2 | Code format: **20 random bytes (160 bits)** from `random_bytes()`, written in Base32 (`A-Z`, `2-7`) as 8 groups of 4 separated by hyphens (39 characters). | "Sufficiently long": 160 bits is far beyond guessable. Base32 without `0/1/8/9` and in groups is easier to read and type back. | Yes (`visitors.php`; new codes only, old ones stay valid) |
| G3 | The hash is computed over the code **normalised**: capital letters, no hyphens, no spaces. | A visitor who types the code in lower case or without hyphens still matches. The returning-visitor step must use the same function. | Hard once visitors exist (same reason as G1) |
| G4 | Name rules: at least 2 letters, at most 100 characters, starts with a letter, only letters of any alphabet, spaces, hyphens, apostrophes and full stops; whitespace is collapsed and trimmed. Digits and symbols are refused. Names need not be unique. | The brief asks for validation but gives no rules. 100 matches `visitors.name`. These rules also keep HTML and control characters out of the table. | Yes (`visitor_name_validate()`). They may refuse a real name with a digit or other symbol. |
| G5 | **Collision check by the database:** the `UNIQUE` key rejects a duplicate hash, then a new code is made and the insert retried, at most **5** times, then the page shows a technical-problem message. | Check-then-insert is not safe when two visitors register at the same moment. A collision with 160-bit codes is practically impossible, so the 5-attempt limit is only a safety stop. | Yes |
| G6 | The code is shown from the **session** (brief), and stays there for **15 minutes** (`REGISTRATION_RESULT_LIFETIME_SECONDS`), then is removed. The result page can be refreshed during that time. A button clears it earlier. | The brief requires that refreshing neither creates a duplicate nor shows a different code. A time limit keeps the plaintext code from sitting in the session file indefinitely. 15 minutes is my choice. | Yes |
| G7 | While the plaintext code is in the session it is **readable by anyone with access to the server's session files** (and to that browser). | A consequence of G6 and of the brief's session requirement. | Reduce the 15 minutes, or accept |
| G8 | The CSRF token is **single-use for a successful registration**: it is replaced after success. A rejected CSRF request with a result still waiting is answered with a redirect to that result instead of an error. | Protects against a double click and the Back button. | Yes |
| G9 | The **session id is not regenerated** after registration. | No privilege change happens. Regenerating it let a simultaneous double click register twice (found in testing). Regenerate it at administrator login instead. | Yes |
| G10 | HTTP status codes: 303 after a successful `POST`; 422 invalid name; 403 invalid CSRF; 400 unknown action; 500 technical failure; 405 for other methods. | Standard meanings. | Yes |
| G11 | Redirects and the form action are **relative** (`register.php`); `APP_URL` is used only to decide whether the session cookie is `Secure`. | Works in a sub-folder (XAMPP) or at the root (Ubuntu) even if `APP_URL` is wrong. A site behind a proxy that ends HTTPS must set `APP_URL` to `https://...` for the cookie to get `Secure`. | Yes |
| G12 | The form has **no HTML `required` attribute**; it does have `maxlength="100"`. | The server is the authority, and the student can see and test the server-side validation in a browser. | Yes |
| G13 | Two helper files were added beyond the `register.php` named in the brief: `includes/security.php` and `includes/visitors.php`. | Keeps the page free of SQL and security code, as `ARCHITECTURE.md` section 2 planned, and lets the logic be tested without a web page. | Yes |
| G14 | Security headers sent: `Content-Security-Policy` (`default-src 'none'; form-action 'self'; frame-ancestors 'none'; base-uri 'none'`), `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `Cache-Control: no-store`. | The pages use no CSS, JavaScript or images, so everything can be blocked. A page that may show a code must not be cached. **If a later step adds images, the policy must be loosened for those pages.** | Yes (`send_security_headers()`) |
| G15 | Double-submit protection relies on PHP's **default file-based sessions**, which let one request per session run at a time. | Found by testing (see `AI_LOG.md`). A custom session handler without locking would need other protection. | Yes |
| G16 | No rate limiting: nothing stops someone from submitting the form repeatedly and creating many visitor rows. | Out of scope for Step 3; listed in section D. | Needs new code |

## I. Decisions made in Step 6 (visitor photo gallery)

**The schema limitation, stated plainly.** The database has no field that separates "this visitor may see their own photograph in their gallery" from "this photograph is approved for the public slideshow". `photos.status` has exactly two values: `active` ("eligible for the slideshow") and `hidden` ("kept but removed from the slideshow"). There is no `deleted` or `rejected` value, and no approval column. No field was invented. The safest reading was chosen instead (I1, I2): the gallery shows only what the slideshow itself would be allowed to show.

| # | Decision | Reason | Easy to change? |
|---|----------|--------|-----------------|
| I1 | **A photograph is visible in the gallery and through `photo.php` only when all three are true:** it belongs to the identified visitor; `status = 'active'`; and a `consents` row exists with `id = photos.consent_id` and the same `visitor_id`. One shared rule (`includes/gallery.php`) is used by both the list and the image endpoint. | The brief: show only photographs with valid consent, respect the status values, never show another visitor's photograph. The composite foreign key already forces the third rule; the `INNER JOIN` checks it again so a damaged record is never shown. | Yes (one constant and the SQL in `includes/gallery.php`) |
| I2 | **A visitor does not see their own `hidden` photographs.** `hidden` can mean "removed from the slideshow" for any reason, and the schema does not say who hid it or why. Nothing in Steps 1-5 can set it; it can only be set directly in the database (or by a later administrator step). | Showing hidden photographs could expose something an administrator removed. Not showing them is the safe direction. If the project later wants "visitors see their own hidden photographs", a separate field or status is needed. | Needs a schema decision |
| I3 | **"Valid consent" means a consent record exists for that visitor and the photograph points at it.** `consent_version` is **not** compared with the current text version (`UPLOAD_CONSENT_VERSION`), so a photograph uploaded under version `1.0` stays visible if the wording later changes to `1.1`. | The project has no rule yet for when an old version stops being valid. Inventing one would change consent behaviour. | Yes (add a condition to the SQL) |
| I4 | **Consent records are never changed by the gallery.** The gallery and `photo.php` only read. | The brief. | n/a |
| I5 | **`photo.php` gives the same answer (404) for "does not exist", "belongs to another visitor", "hidden", "file missing" and "file is not the recorded image type".** A malformed number gets 400, a visitor who is not identified gets 401 (not a redirect, because the answer is an image, not a page). `gallery.php` redirects an unidentified visitor to `identify.php`, like `upload.php`. | Nobody can learn which photo numbers exist by trying them. | Yes |
| I6 | **Page size is 20 (constant `GALLERY_PER_PAGE`).** An invalid `page` value (not a positive whole number) means page 1; a number past the end shows the last page instead of an error. Newest first (`ORDER BY p.id DESC`, which follows the index on `photos.visitor_id`; a newer upload always has a higher id). | Brief: default 20, validate on the server. `id` order avoids a sort and equals upload order. | Yes |
| I7 | **The gallery checks that each file of the current page exists (at most 20 checks per page)** and shows "The image file is not available." instead of a broken image. | A missing file is handled safely and visibly; paths are never shown. | Yes |
| I8 | **Photographs are sent with `Cache-Control: no-store`** (the existing security headers). The browser downloads them again on every view. | The college computers may be shared; a cached private photograph would remain after "End my session". The cost is more traffic. | Yes (`photo.php`) |
| I9 | **No thumbnails.** The page shows each full file scaled by the HTML `width` attribute (160 pixels; no CSS). Twenty photographs of up to 5 MB each can therefore mean a large page. `loading="lazy"` (an HTML attribute) lets the browser postpone images below the screen. | Image resizing needs the GD extension and was listed as not covered (section D); the brief forbids extra libraries. | Needs new code |
| I10 | **Existing files changed:** `includes/security.php` (`send_security_headers()` has one optional parameter, default `false`, that adds `img-src 'self'`; all other pages send exactly the headers they sent before), `upload.php` and `identify.php` (one link line each, to `gallery.php`). | The gallery needs images from this site; visitors need a way to reach it. | Yes |
| I11 | **"End my session" on the gallery is a POST form with the CSRF token that goes to `identify.php` (`action=logout`),** the Step 4 logout. No logout code was duplicated. | A plain logout link could be triggered by another web site. | Yes |
| I12 | **The "status" column shows `Active`** (the only listed value). | Everything else is filtered out (I1). | Yes |
